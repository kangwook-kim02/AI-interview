# 명명 규칙 (이슈 · 브랜치 · 커밋 · PR)

> **이 규칙은 전적으로 AI 에이전트가 적용한다.** 사용자는 "하고 싶은 일"만 말하면 되고,
> 이슈 제목·브랜치명·커밋 메시지의 명명은 `issue-create`/`issue-work` 스킬이 이 문서대로 자동 생성한다.
> 사람이 규칙을 외울 필요 없음 — 관리·가독성을 위해 기계적으로 일관되게 지킨다.

공통 **type** (영어 고정):

| type | 언제 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `design` | 순수 UI/스타일/디자인 변경 (기능 없음) |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정·빌드·의존성·잡일 |
| `test` | 테스트 추가/수정 |

공통 **scope**(선택, 영역 축약): `auth` · `cover-letter` · `interview` · `ai` · `speech` · `recording` · `db` · `ui` · `config` · `infra` · `docs`

---

## 1. 이슈 제목

**형식:** `[영역] 무엇을 한다` — 한국어 OK, 동사로 끝나는 한 줄.

- 영역(한글): 스캐폴딩 · 인프라 · 인증 · 자소서 · 면접 · 디자인 · 문서 · 기타
- **구체적으로, 한 가지만.** 제목만 읽어도 "완료가 뭔지" 떠오르게.

| 좋은 예 | 나쁜 예 |
|---|---|
| `[인증] 이메일 로그인/로그아웃 구현` | `로그인` (너무 막연) |
| `[디자인] 랜딩 페이지 히어로 섹션` | `UI 작업` (범위 불명) |
| `[면접] 꼬리질문 생성 API 추가` | `면접 기능 전부` (너무 큼 → 쪼갠다) |

> 처음 개발하는 사람도 OK: **그냥 하고 싶은 걸 말하면** 스킬이 위 형식으로 제목을 만들어 준다.

## 2. 브랜치명

**형식:** `<type>/<이슈번호>-<슬러그>`

- `type`: 위 표에서 선택 (기능=feat, 버그=fix, 문서=docs, 디자인=design …)
- `슬러그`: **영어 소문자 kebab-case**, 2~4단어, 간결. 한글 금지(ASCII만), 하이픈 구분.
- 예: `feat/5-email-auth` · `design/6-landing-hero` · `fix/12-followup-cap`

## 3. 커밋 메시지 (Conventional Commits)

**형식:** `<type>(<scope>): <제목>`  (scope 선택)

- `제목`: 명령형·간결, **한국어 OK**(type/scope는 영어), 끝에 마침표 없음, 50자 내외.
- **한 커밋 = 한 논리 변경.** 섞지 않는다.
- 본문(선택): *왜* 바꿨는지. 한 줄 비우고 72자 줄바꿈.
- 예:
  - `feat(auth): 이메일 로그인 구현`
  - `fix(interview): 꼬리질문 상한 초과 버그 수정`
  - `design(ui): 랜딩 히어로 코랄 CTA 적용`
  - `docs: PRD에 랜딩 페이지 요구사항 추가`
  - `chore: ESLint 설정 추가`

## 4. PR

- **제목:** `<type>: <요약>` (예: `feat: 이메일 인증 플로우`)
- **본문:** `.github/pull_request_template.md` 사용, 본문에 **`Closes #<이슈번호>`** 로 이슈 연결.
- 브랜치 → main 으로 PR. main 직접 커밋 금지.

---

### 요약 (치트시트)

```
이슈   [영역] 무엇을 한다                         예) [인증] 이메일 로그인 구현
브랜치 <type>/<이슈번호>-<영문-슬러그>            예) feat/5-email-auth
커밋   <type>(<scope>): <제목>                    예) feat(auth): 이메일 로그인 구현
PR     <type>: <요약>  + 본문에 Closes #<번호>    예) feat: 이메일 인증 플로우
```
